# ARTA-MATRYOSHKA — 오류 원인 재측정·단순 요청 제한 비교

2026-10-07. Healing Arty & Arta 공동개발.

## 결론

기본 60회·보조 12회, 총 72회를 직접 실행했다. 기본 비교의 정책 거부를 제외한 오류 24건은
모두 시간 예산이 끝난 시점의 timeout이었다. 보존한 표본에서 record 단계 22건, challenge 단계 2건을 확인했다.
이는 재측정의 시간 경계 관측이며 과거 개별 오류의 원인을 소급 확정하지 않는다.

5초·한 IP 조건에서 요청 제한은 기본 30회/60초 설정으로 30건, 30회/1초 설정으로 150건을 허용했다.
각 조건의 1프로세스 PoW는 평균 286.6건과 255.0건이었다. 이 제한 설정에서는 PoW보다
요청 제한의 수집량 상한이 더 작고 해시 탐색도 필요 없었다. 그러나 정상 사용자 허용량과
부담을 맞추지 않았으므로 일반적인 우열을 입증한 결과는 아니다.

## 직접 검증한 범위

기존 미끼 서버의 `Lab.allowed`를 그대로 불러 같은 합성 자료 HTTP 서버에 적용했다.
전체 미끼 서버를 비교한 것이 아니라 **기존 IP 요청 제한 함수와 정책**을 동일 자료 하네스에서 비교했다.
클라이언트 오류에 HTTP 상태·발생 단계·deadline까지 남은 시간을 추가 기록하여 재측정했다.
실제 AI·GPU·OS 격리 실험은 하지 않았다.

- 기본 비교: direct / no-work / 14비트 pow / rate-limit, 1·2·4프로세스, 5초 × 5회 = 60회.
- 요청 제한 기본값: IP당 60초에 30회, 기존 앱과 같은 이동 시간 창. 모든 클라이언트는 같은 localhost IP.
- 보조 비교: 1프로세스, 30회/1초로 정책 변경, 네 조건 각 5초 × 3회 = 12회.
- 총 측정 예산 360초. 프로세스 준비·종료 시간 별도. 기능 테스트는 측정 전에 끝냈다.
- 자료 100,000개. 자료 소진은 없었고, 실제 자산·인증 정보에 연결하지 않았다.
- 조건별 동일 시간 예산과 자료를 사용했지만 정책의 사용자 허용량은 맞추지 않았다.
- [RFC 6585 §4](https://www.rfc-editor.org/rfc/rfc6585.html#section-4)의 429와
  [RFC 9110 §10.2.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3)의 Retry-After 의미를 확인했다.
  요청 제한 클라이언트는 서버의 대기 안내를 따르고 시간 예산까지만 기다린다.
  따라서 대기를 무시하는 폭주 클라이언트·DDoS 가용성을 시험한 것이 아니다.

`rate-limit`의 HTTP 429는 **의도된 정책 거부**다. 네트워크 오류나 서버 고장과 구분한다.

장기 정상 처리율·여러 IP 우회·정상 사용자 부담까지 비교했다고 주장하지 않는다.

## 오류 발생 단계와 시간 경계

과거 3조건 원본에는 no-work 오류 3·7·10건과 direct 2프로세스 오류 1건이 있었지만 종류가 없었다.
따라서 이번 관측으로 과거 개별 오류 원인을 소급 확정할 수 없다.

이번 기본 비교에서 요청 제한 조건을 제외한 오류 종류 합계: `{"deadline_timeout": 24}`.

| 프로세스 | 조건 | 오류 종류 합계 |
|---:|---|---|
| 1 | direct | `{"deadline_timeout": 1}` |
| 1 | no-work | `{"deadline_timeout": 4}` |
| 1 | pow | `{}` |
| 1 | rate-limit | `{"http_429": 5}` |
| 2 | direct | `{}` |
| 2 | no-work | `{"deadline_timeout": 6}` |
| 2 | pow | `{}` |
| 2 | rate-limit | `{"http_429": 10}` |
| 4 | direct | `{"deadline_timeout": 3}` |
| 4 | no-work | `{"deadline_timeout": 10}` |
| 4 | pow | `{}` |
| 4 | rate-limit | `{"http_429": 20}` |

- `deadline_timeout`: 호출 시작 시 이미 예산이 끝났거나, HTTP timeout 후 예산이 끝난 상태를 직접 관측.
- `timeout_before_deadline`: timeout이 있었지만 아직 전체 시간 예산이 남음. 서버 포화의 단독 증거는 아님.
- `transport_or_decode_error`: 전송·HTTP 처리·JSON 해석 오류. 원인이 더 세분화되어 있지는 않음.
- `http_429`: 서버가 반환한 정책 거부. 서버 카운터 `rate_limit_denials`도 별도로 보존.
- 각 프로세스는 오류 표본 최대 10건의 stage·status·남은 초를 보존하며 종류별 합계는 전부 기록한다.
- 서버가 제공한 건수와 클라이언트가 확인한 건수의 차이도 원본 그대로 남긴다.

HTTP 시간을 남은 예산과 최대 1초 중 작은 값으로 제한하므로 시간 경계 오류는 실험 종료의 영향일 수 있다.
deadline 초과를 관측했다는 사실만으로 서버 포화가 없었다고 결론내리지 않는다.
반대로 당시 오류를 서버 포화라고 단정할 계측도 없다.

## 타당성 판단과 남은 한계

- 단순 IP 요청 제한을 같은 하네스에서 비교하는 것은 현재 코드로 가능하며 직접 실행했다.
- 기본 요청 제한은 한 IP가 확보할 자료 수를 작은 상한으로 제어하고 클라이언트 해시 탐색이 없다.
  이 조건에서 PoW가 요청 제한보다 수집 억제·클라이언트 비용에서 낫다는 근거는 없다.
- 그러나 서로 다른 허용량·정상 사용자 흐름·우회 가능성을 맞추지 않아 요청 제한이 모든 환경에서 우월하다는 결론도 아니다.
- 현재 PoW 모듈 자체는 일반 해시 PoW다. 일반 PoW를 새로 발명했거나 다른 구현보다 우수하다고 주장하지 않는다.
- 실제 AI 검증·재시도 행동, 기존 운영 허니팟, 합성 보호 자산 경계·정상 사용자 부담·가용성은 별도 미검증이다.
- 과거 1프로세스 자료당 CPU 비대칭 약 22.05배는 계산 비용 관측일 뿐 운영 효율·방어 성과가 아니다.
- 병렬화의 증가 크기는 실험 사이에 흔들린다. 재현되지 않은 값을 숨기거나 기대하는 결론에 맞춰 고르지 않는다.
