# ARTA-MATRYOSHKA — 계산 통행료 예비 실험 보고서

공동개발: Healing Arty & Arta.

2026-10-07. 별도 localhost HTTP 마이크로벤치마크이며 기존 미끼 세계에는 통합하지 않았다.

## 조건과 결과

계산 통행료 없음(bits=0)과 SHA-256 14-bit 퍼즐을 비교했다.
각 실행 2초, 클라이언트 스레드 1개/2개, 조건별 3회 반복으로 총 12회 실시했다.
순서 편향을 줄이기 위해 반복마다 조건 실행 순서를 번갈아 바꿨다.
클라이언트와 서버는 별도 프로세스지만 동일 머신의 CPU를 공유한다.

| 클라이언트 스레드 | 비트 | 반복 조회 평균 ± 표본 표준편차 | 최소–최대 | 클라이언트 CPU초 평균 ± 표준편차 | 서버 CPU초 평균 ± 표준편차 |
|---:|---:|---:|---:|---:|---:|
| 1 | 0 | 9934.7 ± 853.4 | 9015–10701 | 1.289 ± 0.012 | 1.139 ± 0.017 |
| 1 | 14 | 167.3 ± 14.0 | 156–183 | 1.940 ± 0.010 | 0.080 ± 0.009 |
| 2 | 0 | 13126.0 ± 694.9 | 12403–13789 | 2.140 ± 0.025 | 1.471 ± 0.065 |
| 2 | 14 | 163.7 ± 4.9 | 158–167 | 2.000 ± 0.004 | 0.072 ± 0.010 |

이 값은 같은 가짜 자료를 반복 조회한 처리량이다. 1/2개 클라이언트가 각각 같은 자료를
재조회한다. 고유 자료의 탈취량 또는 개인정보 유출 방지 성과가 아니다.
서버의 초당 처리량 감소와 클라이언트 계산 증가를 이 조건에서 관측했다.
AI가 속거나 더 오래 생각한다는 증거가 아니다.

## 관련 연구와 이 프로젝트의 질문

계산 통행료는 [Hashcash — A Denial of Service Counter-Measure (Adam Back, 2002, 원문 PDF 미러)](https://cdn.nakamotoinstitute.org/docs/hashcash.pdf)와 [Client Puzzles (Ari Juels·John Brainard, NDSS 1999)](https://www.ndss-symposium.org/ndss1999/cryptographic-defense-against-connection-depletion-attacks/)처럼 클라이언트에 작업 비용을 부과하는 기존 연구 계열입니다. 현대의 [Anubis 공식 설계 문서](https://github.com/TecharoHQ/anubis/blob/main/docs/docs/design/why-proof-of-work.mdx)도 SHA-256 PoW로 작업을 요구하며, [프로젝트 소개](https://github.com/TecharoHQ/anubis)는 AI 크롤러·스크레이퍼의 요청에 대응하는 목적을 명시합니다. ARTA의 통행료는 일반 해시 PoW이며 새로운 암호 기법이나 기존 도구보다 우수한 방어로 주장하지 않습니다. 이 프로젝트가 묻고 싶은 질문은 **“AI 에이전트의 검증·재시도 행동에 미끼 구조와 계산 통행료가 어떻게 반응하며, 목표 도달·탐색·포기·양측 비용에 어떤 차이를 만드는가?”**입니다. 이는 아직 실제 AI 실험으로 검증하지 않은 연구 질문이며, 현재 고정 스크립트의 비용 측정과 구분합니다.

### 14비트 난이도의 의미

해시 출력이 균일하고 서로 다른 nonce 시도를 독립으로 근사하면 성공 확률은 2^-14이고,
성공 해시를 포함한 평균 시도 수는 **2^14 = 16,384회**입니다. 고정된 횟수나 시간 보장이 아니며 실제 탐색량은 달라집니다.
이는 작은 작업량으로, 최적화된 네이티브 코드·GPU에도 유의미한 장벽이 된다고 주장할 수 없습니다.
GPU 비용은 측정하지 않았으므로 “무료”라는 수치적 결론도 내리지 않습니다.
관측 결과는 **이 고정 Python 클라이언트 구현이 추가 솔버 작업 때문에 느려진다**는 범위에서 해석합니다.
향후에는 같은 왕복 대조군·시간·자원 예산으로 비트 수를 바꾸어 고유 수집량과 양측 비용 곡선을 비교할 수 있습니다.
난이도별 곡선은 아직 측정하지 않았습니다. 고유 자료 수집 CLI의 `arta.collectionbench --bits`는 현재 1..18비트를 지원합니다.

## 요청당 서버 비용의 해석

다음 값은 3회 실행의 합계로 계산했습니다. 평균 실행의 비율이나 순수 퍼즐 검증 시간과는 다릅니다.

- 성공 record 응답당: `sum(server_cpu) / sum(records) × 1000` ms.
- 전체 HTTP 요청당: `sum(server_cpu) / sum(requests) × 1000` ms.
- `server_cpu`는 challenge 생성·검증·HTTP·서버 관리 등을 포함한 전체 CPU 비용입니다.

| 스레드 | 비트 | 서버 CPU / 성공 record 응답: ms | 서버 CPU / 전체 HTTP 요청: ms |
|---:|---:|---:|---:|
| 1 | 0 | 0.1147 | 0.1147 |
| 1 | 14 | 0.4773 | 0.2379 |
| 2 | 0 | 0.1120 | 0.1120 |
| 2 | 14 | 0.4418 | 0.2198 |

1스레드 기준 성공 응답당 서버 CPU는 약 **0.1147ms → 0.4773ms**로 증가했습니다.
PoW 조건에는 challenge와 record 요청이 있어 성공 응답 1건이 HTTP 요청 1개와 같지 않습니다.
서버 CPU 합계가 줄어든 것은 수집 처리량·요청 수가 크게 줄어든 조건에서 관측된 결과이며,
성공 응답 하나를 더 싸게 처리하거나 서버 자체가 더 효율적이라는 증거가 아닙니다.
CPU 합계 감소만으로 공격 중 가용성이나 정상 사용자 영향을 판단하지 않습니다.

3회 표본은 작습니다. 범위·표준편차는 관측된 흔들림이며 모집단의 신뢰구간이나 장기 안정성 보장이 아닙니다.

## 구현한 기능

- 외부 주소를 인자로 받지 않는 localhost 전용 별도 실험 서버.
- 합성 자료 네 종류만 제공. 실제 파일/계정/서버와 연결하지 않음.
- 퍼즐에 조회할 자료 ID를 연결하고 만료 10초·일회성 적용.
- 미완료 퍼즐 최대 128개, 입력 본문 1 KiB, 난이도 최대 18비트.
- 성공 검증은 SHA-256 한 번. 생성/검증/HTTP 등 서버 전체 CPU를 별도로 측정.
- 재사용·잘못된 자료 연결·만료·잘못된 입력 거부 테스트.

퍼즐은 bearer 방식이며 사용자 인증 또는 기기 연결은 아니다. 세션 간 전달을 막지 않는다.
현재 실험 서버는 기본 애플리케이션과 분리되어 있고 실제 서버 방어에는 적용하지 않았다.

## 안전 검증과 한계

새 network namespace 생성은 실행 환경 권한 때문에 실패했다.
Docker도 이 환경에 없어 OS/네트워크 격리 검증을 완료하지 못했다.
별도 프로세스는 샌드박스가 아니다. 따라서 신뢰할 수 없는 공격 코드나 실제 AI 도구를
실행하지 않고 우리가 작성한 제한된 합성 조회 스크립트만 실행했다.

실제 300초 실험은 하지 않았다. 2초의 작은 난이도 기능/처리량 비교를 먼저 수행했다.
2개 스레드는 Python GIL과 동일 CPU 영향을 받으므로 GPU·다중 프로세스·분산 병렬화
저항성을 증명하지 않는다. 일반 해시 PoW는 병렬화 가능하다.
별도 검증 조회 전략·실제 AI·실제 보호 자료 비교도 미실시다.
서버 단일 처리와 클라이언트 구현 차이가 결과에 영향을 준다.
OS 전체 자원 상한/메모리 비용/전력 비용은 측정하지 않았다.
퍼즐을 건너뛰고 다른 취약점을 노리는 공격은 막았다고 주장할 수 없다.

## 실행과 다음 단계

```bash
python -m unittest discover -s tests -v
python -m arta.tollbench --seconds 2 --repeats 3
```

CLI는 실행당 최대 300초를 허용하지만 총 실행은 클라이언트 2조건 × 통행료 2조건 × 반복 수다.
기본은 12회 × 2초다. `--seconds 300`을 지정하면 전체가 5분이 아니라 약 1시간일 수 있다.
결과 JSON은 stdout으로 출력한다. 기존 보고서와 원본 결과를 덮어쓰지 않는다.

이 보고서는 당시 2초·스레드 실험 기록입니다. 이후 별도 CPU 프로세스·고유 자료 수집·무계산 2왕복 비교는
[대조 실험 보고서](CONTROLBENCH-REPORT.md)에 기록했습니다. 과거 결과와 혼합하지 않습니다.

당시 제안한 다음 순서는 검증된 외부 격리 환경 확보 → 300초 반복 측정 → 다중 프로세스·조기 포기·검증 전략 비교
→ 실제 AI 계측이다. 연구 목적에 맞는 합성 자료의 고유 수집량도 따로 측정해야 한다.
